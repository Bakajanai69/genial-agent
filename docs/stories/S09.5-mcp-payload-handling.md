## 📍 Contexte

Le **dogfooding S09 inspection MCP** (cf.
[`docs/inspection-mcp-vs-agent.md`](../inspection-mcp-vs-agent.md))
a révélé que **3 des 5 outils Pappers testables** retournent
systématiquement des payloads largement au-dessus de la borne agent
``_TOOL_RESULT_MAX_CHARS = 16 000`` chars (cf.
``src/genial_agent/agent.py:399``). La troncature actuelle est une
simple coupe par caractères en cherchant un délimiteur propre, ce qui
sur des JSON Pappers triés croissants par année **fait perdre les
données récentes au profit des anciennes**.

L'agent **a conscience** de la troncature et le signale plutôt que
d'inventer (cf. dogfooding D-S09 réponse Carrefour CA : *"Non
directement lisible dans l'extrait retourné, données tronquées"*) —
la robustesse comportementale est intacte. Mais la **qualité** des
réponses sur les questions financières détaillées et les
cartographies de dirigeants est dégradée.

### Contraintes utilisateur (input phase 1, 2026-04-25)

L'utilisateur a explicité deux contraintes qui orientent le design :

1. **Pas de hardcoding** : pas de logique métier figée par champ
   (CA, résultat net, …), par entité, par année, par type d'usage.
   Les questions des évaluateurs vont varier, et un wrapper qui
   choisit *à l'avance* quelles sections garder rate les questions
   exotiques.
2. **Fiabilité utilisateur > coût compute** : le retour à
   l'utilisateur doit être **le plus fiable possible à partir des
   vraies données Pappers**. Si la solution coûte plus cher en
   tokens / latence, c'est acceptable tant que la fiabilité gagne.

Cette story doit produire une **stratégie robuste, user-ready, et
adaptative** au type de réponse retournée par chaque tool, sans
hardcoder de troncature aveugle ni de paramètres figés (les années
et les demandes utilisateur changent).

4. **Tools de retrieval** exposés à l'agent :

     contexte sur la donnée brute.
5. **Intégration agent.py** : interception locale dans la boucle
   tool-use (pas un appel Pappers, donc pas un crédit consommé,
   mais bien un ``tool_calls_count`` incrémenté pour rester sous le
   contrat S07).
6. **Tests live** sur les 3 entités du smoke test Pappers (LVMH /
   BNP / Carrefour) prouvant que les questions :
   - *"Quel est le dernier CA de Carrefour ?"*
   - *"Quels sont les mandats de Bernard Arnault ?"*
   - *"Compare santé financière Carrefour vs Casino sur 3 ans"*
   - *"Liste filiales LVMH"*

   renvoient des données **récentes et complètes** (cf. métrique
   succès §"Métrique de succès objective").
7. **Documentation** : update ``inspection-mcp-vs-agent.md``
   (tableau "après" en regard du "avant"), update système prompt
   (1-2 lignes génériques sur l'index), update README "Next steps".

**Conclusions transversales** :

- Le « petit » payload (sirenisateur, recherche-entreprises avec

- Le « moyen » payload (cartographie 20-50 K) tient sous 50 K.

- Le « gros » payload (comptes 100 K-700 K, recherche-dirigeants

- Seuil d'offload : **12 000 chars** (en dessous, retour direct).

- Cap lookups par turn : **5** (laisse 2 calls Pappers + 5 inspects

## 🧭 Approches évaluées (recherche phase 1, 2026-04-25)

### A — Programmatic Tool Calling Anthropic (`code_execution_20260120`)

> Référence officielle : [platform.claude.com/docs/.../programmatic-tool-calling](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling)

- **Statut 2026-04** : **GA** (sortie de beta), pas de header beta.
- **Modèles supportés** : Opus 4.7, Opus 4.6, Sonnet 4.6, Opus 4.5,
  Sonnet 4.5. **Haiku 4.5 NON supporté** (vérifié dans la matrice
  officielle).
- **Restriction MCP** : *"Tools provided by an MCP connector cannot
  currently be called programmatically"*. Notre client MCP custom
  (`mcp_pappers.py`) **contourne** cette restriction parce qu'on
  expose les tools Pappers comme tools Anthropic classiques (pas via
  MCP connector). Mais ça reste un workaround.
- **Pour** : sandbox géré, Anthropic-natif, ~37 % réduction tokens
  sur tâches multi-tool.
- **Contre** : **force Sonnet** sur U1 simples → casse l'avantage
  routing S04 (Haiku par défaut). Effort 3-4 j. Sandbox containers
  à observer (lifecycle 4.5 min idle / 30 j max).
- **Verdict** : ❌ écarté, Haiku non supporté + impacte routing.

### B — Filesystem offload (Deep Agents / LangChain)

> Référence : [langchain.com/blog/context-management-for-deepagents](https://www.langchain.com/blog/context-management-for-deepagents)

- **Pattern** : tool result > 20 K tokens → offload à
  `read_file/grep/ls/glob`. Fallback summarization à 85 % context.
- **Pour** : pattern éprouvé, large adoption.
- **Contre** : ajoute LangChain comme dep (cahier §9 dit *"Pas de
  framework agent custom"*). Le filesystem doit survivre entre tours
  user → impacte cold start Railway (sleep). Multi-session ambigu.
- **Verdict** : ❌ écarté tel quel. **L'idée** (offload + tools de
  retrieval) est reprise dans l'approche J retenue, sans la dep.

### C — Sub-agent synthesizer Haiku-extracteur

- **Pour** : adaptatif sur la question, léger à coder, cohérent avec
  le pattern Haiku-critic S05 C6.
- **Contre** : **synthèse LLM = lossy + non-vérifiable**. Risque
  d'hallucination de chiffres. Perte de nuances que la question
  initiale n'avait pas anticipées (« et leurs adresses ? » après
  un résumé qui les a drop).
- **Verdict** : ❌ écarté en primary (contredit la contrainte
  utilisateur "fiabilité max sur les vraies données"). Garde un rôle
  **fallback de dernier recours** : si l'agent peine sur 3 lookups,
  synthétiser ce qu'il a déjà vu (cf. §"Fallback de dégradation").

### D — Dynamic filtering serveur (Anthropic web_search/web_fetch)

- **Statut 2026-04** : pattern Anthropic-natif sur les tools officiels
  uniquement.
- **Verdict** : ❌ N/A — Pappers est un MCP tiers, on ne contrôle pas.

### E — `clear_tool_uses_20250919` (context editing beta)

> Référence : [platform.claude.com/docs/.../context-editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)

- **Statut 2026-04** : **beta**, header
  `context-management-2025-06-27`.
- **Modèles** : *"available on all supported Claude models"* →
  Haiku 4.5 OK.
- **Pour** : 0 dev (juste activer + config).
- **Contre** : **ne corrige pas la troncature initiale**. Le tool
  result est tronqué à 16 K **avant** d'être ajouté à l'historique.
  Clear ne récupère pas les chars perdus. Utile en multi-turn long,
  pas pour notre cas.
- **Verdict** : ❌ ne résout pas. À combiner éventuellement (à
  surveiller post-S09.5).

### F — MCP 2.4 sampling profiles

- **Statut** : spec 2025-11-25, Pappers ne le supporte pas.
- **Verdict** : ❌ N/A.

### F' — Wrapper déterministe per-tool (extraction de champs figés)

- **Pour** : déterministe, 0 LLM par appel, auditable.
- **Contre** : **HARDCODE** des champs (CA, résultat, effectif,
  date_bilan, …). Ne s'adapte pas aux questions exotiques. **Refusé
  explicitement par l'utilisateur** ("je ne veux pas hardcoder des
  comportements type date, entreprise ou autre").
- **Verdict** : ❌ écarté par contrainte produit.

### G — Pagination explicite + agent qui itère

- **Pour** : 15 min de dev (system prompt).
- **Contre** : tape le cap 7 sur Arnault / Pinault. Ne s'applique pas
  à `comptes-entreprise` (pas de pagination par année dans la même
  request).
- **Verdict** : ❌ pas en primary. Conservé comme **complément**
  pour `recherche-dirigeants` uniquement (1 ligne de prompt) si la
  phase 2 mesure que ça aide marginalement.

### H — User-intent-aware extraction

- **Pour** : potentiellement intelligent.
- **Contre** : complexe à orchestrer, fragile (l'agent doit
  pré-deviner la structure JSON Pappers), interaction routing/caps
  floue.
- **Verdict** : ❌ trop R&D pour le scope MVP.

### **J — Generic Payload Vault + LLM-driven retrieval (RETENUE)**

L'approche retenue. Inspirée du pattern Deep Agents (filesystem
offload) **sans LangChain**, et du pattern Anthropic Memory tool
**sans la convention `/memories/` ni la persistence cross-session**.

- **Cœur** : tout payload Pappers > 12 K chars est stocké dans un
  dict in-memory scoped session. L'agent reçoit en lieu et place un
  index générique compact + un `payload_id`. L'agent **décide
  lui-même** quoi extraire selon la question utilisateur, via 2 nouveaux
  tools `payload_inspect` (JSONPath) et `payload_search` (regex). Les
  données extraites sont **verbatim** (zéro hallucination).
- **Générique** : aucun champ Pappers hardcodé, aucune logique métier
  par tool. Marche pour tout JSON volumineux (futurs MCP inclus).
- **User-aware** : la question utilisateur arrive au LLM avec
  l'index → le LLM choisit les paths à lire selon la question.
- **Fiabilité max** : `payload_inspect(json_path)` retourne **la
  valeur littérale** du JSON original, garantie verbatim par walk
  déterministe. Pas d'extraction LLM lossy.
- **Compute cost** : ~1-3 K tokens d'index injectés au tool result +
  1-3 lookups de ~2-4 K tokens. Total : ~10-15 K tokens / payload
  gros (vs 16 K tronqué actuellement). **Un peu plus de tokens, mais
  données complètes et vérifiables**. Trade-off accepté par
  l'utilisateur.

## 🏗 Décision phase 1 — Architecture J détaillée

### 1. Module `src/genial_agent/payload_vault.py` (nouveau)

```python
"""Payload Vault — offload générique des tool results MCP volumineux.

Scoped session (jamais sur disque, jamais cross-session). Stocke les
payloads bruts > OFFLOAD_THRESHOLD_CHARS et expose un index compact
au LLM, qui peut ensuite ré-interroger via payload_inspect /
payload_search.

Aucune logique métier Pappers : ne sait que naviguer du JSON
arbitraire (dict / list / scalaire).
"""

from __future__ import annotations

import json
import re
import secrets
from dataclasses import dataclass, field
from typing import Any

OFFLOAD_THRESHOLD_CHARS = 12_000  # cf. §"Données factuelles"
INDEX_BUDGET_CHARS = 4_000
LOOKUP_MAX_CHARS_DEFAULT = 8_000
PREVIEW_HEAD_CHARS = 400
PREVIEW_TAIL_CHARS = 400
SKELETON_MAX_DEPTH = 3
SKELETON_MAX_KEYS_PER_LEVEL = 30


@dataclass
class PayloadVault:
    """Vault session-scoped (rangé sur ConversationState)."""

    _store: dict[str, str] = field(default_factory=dict)  # payload_id → raw JSON

    def store(self, raw: str) -> str:
        """Range un payload brut, retourne un payload_id court."""
        pid = f"p_{secrets.token_hex(4)}"
        self._store[pid] = raw
        return pid

    def get(self, pid: str) -> str | None:
        return self._store.get(pid)

    def __len__(self) -> int:
        return len(self._store)


def build_index(raw: str, payload_id: str) -> dict[str, Any]:
    """Construit un index générique du payload — pas de logique
    métier. Profile : squelette JSON, tailles d'arrays, previews."""
    parsed = _safe_parse_json(raw)
    return {
        "_payload_id": payload_id,
        "_size_chars": len(raw),
        "_skeleton": _skeleton(parsed, depth=0),
        "_array_sizes": _collect_array_sizes(parsed),
        "_preview_head": raw[:PREVIEW_HEAD_CHARS],
        "_preview_tail": raw[-PREVIEW_TAIL_CHARS:] if len(raw) > PREVIEW_HEAD_CHARS else "",
        "_inspect_hint": (
            "Use payload_inspect(payload_id, json_path) to read a specific subtree, "
            "or payload_search(payload_id, regex) to grep the raw JSON. "
            "Paths use dotted notation: '$.comptes[0].chiffre_affaires' or "
            "'comptes[0].chiffre_affaires'. Indices are 0-based."
        ),
    }


def inspect(raw_json: str, json_path: str, max_chars: int) -> str:
    """Walk déterministe sur le JSON. Retourne la valeur encodée en
    JSON, tronquée à max_chars avec marker explicite si nécessaire."""
    parsed = _safe_parse_json(raw_json)
    value = _walk(parsed, json_path)
    encoded = json.dumps(value, ensure_ascii=False, indent=2)
    if len(encoded) > max_chars:
        return encoded[:max_chars] + "\n…[lookup truncated]"
    return encoded


def search(raw_json: str, pattern: str, max_matches: int = 10,
           context_chars: int = 200) -> list[dict[str, Any]]:
    """Regex search avec contexte. Retourne {match, context, position}."""
    try:
        rx = re.compile(pattern, re.IGNORECASE | re.MULTILINE)
    except re.error as exc:
        return [{"error": f"invalid regex: {exc}"}]
    out: list[dict[str, Any]] = []
    for m in rx.finditer(raw_json):
        if len(out) >= max_matches:
            break
        start = max(0, m.start() - context_chars // 2)
        end = min(len(raw_json), m.end() + context_chars // 2)
        out.append({
            "match": m.group(0),
            "position": m.start(),
            "context": raw_json[start:end],
        })
    return out


# --- Helpers privés (squelette JSON, walk JSONPath) ---

def _safe_parse_json(raw: str) -> Any:
    try:
        return json.loads(raw)
    except (ValueError, TypeError):
        return {"_raw": raw[:1000], "_note": "payload non-JSON"}


def _skeleton(node: Any, depth: int) -> Any:
    if depth >= SKELETON_MAX_DEPTH:
        return _summarize(node)
    if isinstance(node, dict):
        items = list(node.items())[:SKELETON_MAX_KEYS_PER_LEVEL]
        return {k: _skeleton(v, depth + 1) for k, v in items}
    if isinstance(node, list):
        if not node:
            return []
        return [f"<{type(node[0]).__name__}>[{len(node)} items]"]
    return _summarize(node)


def _summarize(node: Any) -> str:
    if isinstance(node, str):
        return f"<str:{len(node)}>"
    if isinstance(node, (int, float, bool)) or node is None:
        return f"<{type(node).__name__}>"
    if isinstance(node, dict):
        return f"<dict:{len(node)} keys>"
    if isinstance(node, list):
        return f"<list:{len(node)}>"
    return f"<{type(node).__name__}>"


def _collect_array_sizes(node: Any, prefix: str = "$",
                         out: dict[str, int] | None = None) -> dict[str, int]:
    if out is None:
        out = {}
    if isinstance(node, dict):
        for k, v in node.items():
            _collect_array_sizes(v, f"{prefix}.{k}", out)
    elif isinstance(node, list):
        out[prefix] = len(node)
        if node and isinstance(node[0], (dict, list)):
            _collect_array_sizes(node[0], f"{prefix}[*]", out)
    return out


_PATH_SEGMENT = re.compile(r"([^.\[\]]+)|\[(\d+)\]")


def _walk(node: Any, path: str) -> Any:
    """Walk path '$.foo.bar[0].baz' ou 'foo.bar[0].baz'."""
    cleaned = path.lstrip("$").lstrip(".")
    if not cleaned:
        return node
    segments = [
        (m.group(1) or m.group(2))
        for m in _PATH_SEGMENT.finditer(cleaned)
    ]
    cur: Any = node
    for seg in segments:
        if seg.isdigit():
            idx = int(seg)
            if not isinstance(cur, list) or idx >= len(cur):
                return {"_error": f"index {idx} out of range at '{path}'"}
            cur = cur[idx]
        else:
            if not isinstance(cur, dict) or seg not in cur:
                return {"_error": f"key '{seg}' missing at '{path}'"}
            cur = cur[seg]
    return cur
```

**Pourquoi cette interface** :

- `_skeleton` produit une carte de profondeur 3 du JSON, avec arrays
  réduits à `<type>[N items]` → lisible par le LLM, capable de cibler
  un index (`comptes[5]`).
- `_collect_array_sizes` retourne explicitement les tailles d'arrays
  → l'agent sait qu'il y a 42 comptes et peut viser
  `comptes[41]` pour le plus récent (ou `comptes[0]` selon l'ordre,
  qu'il déduit du `_preview_head/_preview_tail`).
- `_walk` accepte `$.a.b[0].c`, `a.b[0].c`, `a/b[0]/c` (canonisé).
  Pas de dépendance JSONPath (jsonpath-ng = +1 dep, pas justifié pour
  un walk deterministe simple).

### 6. Cache & idempotence

- **Le vault n'est PAS cross-session**. Chaque session Chainlit a son
  propre `state.payload_vault`. Évite la fuite cross-tenant et le
  problème cold start Railway.
- **Le cache S02 (`mcp_cache.py`) reste inchangé** : il cache la
  réponse Pappers brute. L'offload arrive en aval (post-cache), donc
  le cache 24 h continue de protéger les crédits.
- **Pas de TTL** sur le vault : la session vit le temps du chat
  Chainlit, le vault meurt avec elle. Pas de fuite mémoire long
  terme (cap implicite par durée de session).

### 7. Fallback de dégradation

Si l'agent fait 5 lookups sans converger (cap local atteint sur un
seul tour) → injecter automatiquement un message synthèse en dernier
recours. **C'est l'unique cas où on accepte une synthèse LLM** : le
budget de lookups est épuisé, mieux vaut une synthèse claire qu'une
réponse incomplète. Cf. §"Critères d'acceptation" pour la métrique.

|---|---|

#### Politique d'économie crédits Pappers — résumé opérationnel

| Règle | Mécanisme | Vérification |
|---|---|---|
| **Cache 24 h tool-level** déjà en place (S02) | `mcp_cache.py` clé = `(tool_name, args_hash)` | `mcp_cache_hit` event dans structlog. Trace doit montrer `was_cached: true` après le 1er appel d'une combinaison `(tool, args)` |
| **Re-jouer = gratuit** tant que les args MCP ne varient pas | Cache 24 h | Si l'agent change ses args entre runs (par ex. `annee=2023` puis `annee=2024`), il consomme 2× — observer dans la trace |
| **Limiter à 3 entités** pour le dogfooding itératif | LVMH / BNP / Carrefour pré-warmées par `prewarm_cache` | Tableau de bord : `stats.pappers_calls_today()` doit rester proche de 0 après les 3 prewarms |
| **Pas de re-test sur "déjà vert"** | Tracking par tableau d'itération (cf. §Step 1) | Le dev tient un journal `traces/S095_iterations.md` qui liste {prompt, tool, statut OK/KO, run n°}. Un cas OK 3 runs consécutifs n'est plus rejoué tant qu'aucune modif touchant son code-path n'est faite |
| **Ne pas activer `make test-integration` complet** sauf à la fin | `pyproject.toml` exclut le marker `integration` par défaut | Cf. règle README "Décisions de cohérence" §6 |
| **Mode dégradé cache-only** comme filet de sécurité | `credit_guard.degraded()` (S07) lit `DAILY_PAPPERS_CREDITS_CAP=100` | Si on dépasse en dev, le cache prend le relais sur les 3 entités golden |

**Ordre de grandeur attendu pour la phase 2 complète** :

- 3 entités golden × 3 tools = 9 combinaisons uniques.
- ~3 itérations / combinaison avant convergence = 27 appels
  uniques en pire cas.
- Le cache absorbe les 9 itérations × N reruns subséquents → **~30
  crédits Pappers consommés** sur toute la phase 2 (sur un cap
  journalier 100, marge confortable).

Si la trace montre > 50 appels Pappers cumulés sur une journée de
dev, **investiguer** : probable variation d'args inattendue côté
agent ou cache TTL trop court. **C'est un signal d'arrêt**, pas un
"on verra plus tard".

## 🧠 Annexe — Pourquoi cette approche bat les autres sur les contraintes utilisateur

| Contrainte utilisateur | A (Programmatic) | B (FS offload) | C (Synthesizer) | F' (Wrapper) | **J (retenue)** |
|---|:-:|:-:|:-:|:-:|:-:|
| Pas de hardcoding (date/entreprise/champs) | ✅ | ✅ | ✅ | ❌ | ✅ |
| User-aware (s'adapte à la question) | ✅ | ✅ | ✅ | ❌ | ✅ |
| Fiabilité max sur les vraies données | ✅ déterministe | ✅ verbatim | ⚠ LLM lossy | ✅ déterministe | ✅ verbatim |
| Compatible Haiku 4.5 (routing S04) | ❌ Opus/Sonnet only | ✅ | ✅ | ✅ | ✅ |
| Compatible MCP custom Pappers | ⚠ workaround | ✅ | ✅ | ✅ | ✅ |
| Pas de framework externe (cahier §9) | ✅ | ❌ LangChain | ✅ | ✅ | ✅ |
| Pas de filesystem persistant Railway | ✅ | ❌ | ✅ | ✅ | ✅ |
| Effort raisonnable (< 2 j) | ❌ 3-4 j | ⚠ 2 j | ✅ 1 j | ✅ 1 j | ✅ 1.5 j |
| Compute cost | ⚠ sandbox $ | ⚠ FS I/O | ⚠ +Haiku call | ✅ 0 | ⚠ +1-3 inspect calls |

**Verdict** : J est la seule approche qui coche **toutes** les
contraintes utilisateur, avec un trade-off compute cost (~10-15 %
tokens en plus par tour qui touche un gros payload) accepté en
échange de la fiabilité maximale demandée.
