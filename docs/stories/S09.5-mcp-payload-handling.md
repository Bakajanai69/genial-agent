## 📍 Contexte

Le **dogfooding S09 inspection MCP** (cf.
[`docs/inspection-mcp-vs-agent.md`](../inspection-mcp-vs-agent.md))
a révélé que **3 des 5 outils Pappers testables** retournent
systématiquement des payloads largement au-dessus de la borne agent
``_TOOL_RESULT_MAX_CHARS = 16 000`` chars (cf.
``src/genial_agent/agent.py:399``). La troncature actuelle est une
simple coupe par caractères en cherchant un délimiteur propre, ce qui
sur des JSON Pappers triés croissants par année **fait perdre les
données récentes au profit des anciennes**.

L'agent **a conscience** de la troncature et le signale plutôt que
d'inventer (cf. dogfooding D-S09 réponse Carrefour CA : *"Non
directement lisible dans l'extrait retourné, données tronquées"*) —
la robustesse comportementale est intacte. Mais la **qualité** des
réponses sur les questions financières détaillées et les
cartographies de dirigeants est dégradée.

Cette story doit produire une **stratégie robuste, user-ready, et
adaptative** au type de réponse retournée par chaque tool, sans
hardcoder de troncature aveugle ni de paramètres figés (les années
et les demandes utilisateur changent).

## 🧭 Approches à évaluer (sans biais — l'agent d'élicitation tranche)

Les approches ci-dessous sont issues de la recherche web 2026 (cf.
sources en fin de doc). **Aucune n'est pré-validée**. La phase 1
doit :

1. Approfondir chaque approche avec une recherche complémentaire.
2. Mesurer le coût d'implémentation en heures.
3. Mesurer le coût opérationnel (tokens, latence, $).
4. Évaluer la robustesse face aux variantes Pappers (un nouveau tool,
   une nouvelle entité-type).
5. Valider la compatibilité avec le pipeline S05 (caps, validator,
   critic) — chaque approche doit pouvoir être branchée sans
   bouleverser le contrat d'events `run_guarded_turn`.
6. **Recommander une approche**, ou une combinaison (ex: A + G court
   terme + F' moyen terme), avec arguments.

### A — Programmatic Tool Calling (Anthropic, beta `advanced-tool-use-2025-11-20`)

> *"Claude orchestre les outils via du code Python dans un sandbox
> `code_execution_20250825`. Les résultats intermédiaires restent
> dans l'environnement d'exécution sandboxé et ne polluent pas le
> contexte du modèle. Réduction 37 % de la consommation tokens en
> tâches complexes (de ~43 K à ~27 K)."*

- Pour : Claude lui-même fait le slicing intelligent ; pas de code
  Pappers-spécifique à maintenir ; Anthropic-native.
- Contre : header beta, sandbox additionnel à provisionner et
  observer, sécurité (Claude écrit du code qu'on exécute), modèle
  Sonnet 4.5+ requis dans la doc Anthropic (pas confirmé pour Haiku
  4.5 — à vérifier en phase 1).
- Effort estimé : 3-4 j.
- Modèles supportés : à vérifier explicitement pour Haiku 4.5.
- Coût additionnel : tokens code execution + sandbox compute.

### B — Filesystem offload (Deep Agents SDK / LangChain)

> *"Au-delà de 20 K tokens, le tool result est écrit sur disque, et
> l'agent ne voit qu'un chemin + preview 10 lignes. Il peut faire
> grep/cat plus tard si besoin."*

- Pour : élégant, large dans son adoption (LangChain), résout le
  problème générique (pas seulement Pappers).
- Contre : nécessite des tools `ls`/`grep`/`cat` exposés à l'agent
  (qu'on ne fournit pas aujourd'hui) ; le filesystem doit survivre
  entre tour utilisateur (impacte cold start Railway sleep + impacte
  isolation par session-id) ; ajoute une boucle d'appels (latence).
- Effort estimé : ~2 j (wrapper + 3 nouveaux tools côté
  ``mcp_pappers.py`` + tests).
- Coût additionnel : disque + latence d'1-2 tool calls
  supplémentaires.

### C — Sub-agent synthesizer (LLM intermédiaire)

> *"Avant d'injecter le tool result dans le state principal, lance
> un Haiku 4.5 dédié qui résume / extrait selon la question
> utilisateur."*

- Pour : adaptatif sur la question utilisateur ; léger à implémenter
  ; cohérent avec le pattern Haiku-critic S05 C6.
- Contre : ajoute un point de défaillance ; risque d'hallucination
  de la synthèse (Haiku peut mal résumer un JSON inhabituel) ;
  perte de nuances que la question utilisateur n'avait pas
  anticipées (« et leurs adresses ? » après le résumé).
- Effort estimé : ~1 j.
- Coût additionnel : 1-2 K tokens Haiku par gros payload, latence
  +500 ms à +1 s.

### D — Dynamic filtering serveur (Anthropic 2026, web_search/web_fetch)

> *"Les tools officiels web_search/web_fetch supportent un filtre
> dynamique : Claude écrit du code dans un sandbox pour post-process
> les résultats avant qu'ils touchent le context."*

- Pour : pattern Anthropic-natif récent, propre.
- Contre : **non disponible** sur Pappers MCP (serveur tiers, on ne
  contrôle pas) ; cité ici pour info uniquement, à reconsidérer si
  Pappers expose un jour ce pattern.
- Effort estimé : n/a.

### E — Automatic tool call clearing (Anthropic beta)

> *"Claude clear automatiquement les anciens tool results en
> approchant la limite tokens, allowing for more efficient context
> management in multi-turn tool use scenarios."*

- Pour : 0 dev, juste activer.
- Contre : ne corrige **pas** la perte d'info au moment de la
  lecture initiale du tool result (il est tronqué dès le 1er
  appel) — ne résout pas notre problème spécifique.
- Effort estimé : 5 min (activer le beta header).
- À combiner avec une autre approche.

### F — MCP 2.4 sampling control profiles (spec novembre 2025)

> *"La spec MCP 2.4 ajoute des profils de prompt sanitization +
> result filtering + sampling thresholds."*

- Pour : standardisé.
- Contre : Pappers ne le supporte pas (on est sur MCP 1.x). À
  surveiller, pas actionnable maintenant.

### G — Pagination explicite + agent qui itère

> *"L'agent appelle `par_page=10`, page 1, voit les résultats,
> demande page 2 si besoin."*

- Pour : 15 min de dev (system prompt seulement) ; standard.
- Contre : **tape le cap 7 tool calls / tour** sur les cas
  pluri-mandats (Arnault, Pinault) — cas réels de la démo. Ne
  s'applique pas à `comptes-entreprise` (Pappers ne pagine pas par
  année dans la même request).
- Effort estimé : 15 min pour l'instruction de pagination dans le
  system prompt.
- À combiner avec une autre approche.

### F' — Adaptive per-tool wrapper (déterministe)

> *"Pour chaque tool gros, un post-traitement déterministe en
> Python pur (pas de LLM, pas de sandbox) qui extrait les sections
> pertinentes avant la borne 16 K."*

- Pour : déterministe (testable unitairement), pas de coût
  additionnel par-call, pas de point de défaillance LLM, le code
  reste lisible et auditable.
- Contre : code Pappers-spécifique (besoin d'un wrapper par tool),
  doit être maintenu si Pappers change ses schémas, ne s'adapte
  **pas** à des questions utilisateur exotiques (ex: "donne-moi
  toutes les liasses comptables détaillées de Carrefour 2017" → on
  les a drop par défaut).
- Effort estimé : ~1 j (3 wrappers : `comptes-entreprise`,
  `recherche-dirigeants`, `cartographie-entreprise` + tests).
- Coût additionnel : 0.

### H — User-intent-aware extraction

> *"Avant le call MCP, regarder la question utilisateur, déterminer
> quelles sections du payload sont pertinentes, et au retour du
> MCP, filtrer le payload selon ces sections."*

- Pour : potentiellement le plus intelligent.
- Contre : complexe à orchestrer, fragile (l'agent doit pré-deviner
  la structure JSON Pappers), interaction avec le routing S04 et
  les caps S05 à clarifier.
- Effort estimé : 3-5 j, R&D non bornée.

### I — Hybride (mix de plusieurs approches)

Exemple : G (pagination) court terme + F' (wrapper déterministe)
moyen terme + C (synthesizer) seulement comme **fallback** si le
wrapper ne suffit pas. La phase 1 doit explicitement évaluer si une
combinaison hybride bat les approches monolithiques.

## 🔬 Questions ouvertes pour l'agent d'élicitation

Liste non-exhaustive — la phase 1 doit y répondre, ou justifier de
les laisser ouvertes.

1. **Métrique de succès objective** : comment juger qu'une approche
   est « assez bonne » ? Proposition : sur les 3 prompts golden
   (LVMH / BNP / Carrefour CA + Arnault mandats) :
   - Nombre de SIREN distincts cités dans la réponse finale ≥ N
   - Année du dernier bilan cité = année courante - 1 minimum
   - Pas de message *"données tronquées"* dans la réponse finale
2. **Granularité du wrapper** : un wrapper unique avec table de
   policies par tool ? Ou un wrapper par tool ?
3. **Contrat d'events** : faut-il un nouvel event
   ``tool_result_compacted`` pour la trace ? Ou laisser le pipeline
   inchangé et instrumenter via structlog uniquement ?
4. **Cache** : les wrappers doivent-ils être appliqués **avant** le
   cache 24 h (cf. ``mcp_cache.py``) ou **après** ? Trade-off : avant
   = cache plus petit ; après = on peut servir des variantes de
   compaction sans relire Pappers.
5. **Fallback** : que faire si le wrapper extrait moins de N
   caractères (signe que le payload Pappers a un schéma non prévu) ?
   Renvoyer le payload tronqué brut ? Échouer ? Critic-flag ?
6. **Tests adversariaux S09** : est-ce que le pack adversarial
   tient toujours après l'implémentation ? Le runner `test_S09_adversarial`
   doit être ré-exécuté en phase 2 et valider 9/10 minimum.
7. **System prompt** : doit-il être mis à jour pour pousser à
   utiliser certains paramètres tools (ex: `annee=`) ? Ou la
   modification reste-t-elle 100% côté wrapper (pas de bricolage
   prompt) ?
8. **Régression caps** : le wrapper réduit-il les tokens vus côté
   Claude → on peut peut-être ré-baisser ``MAX_TOKENS_PER_SESSION``
   de 80 K à 50 K (revert d'un fix S08) ? À mesurer.
9. **Approche A et le sandbox Anthropic Code Execution** : disponible
   pour Haiku 4.5 ? Notre routeur dispatch Haiku par défaut → si A
   exige Sonnet pour fonctionner, ça change le ratio Haiku/Sonnet
   (impact $ et latence).
10. **Modèles 2026** : la phase 1 doit re-vérifier que les versions
    pinnées (`anthropic>=0.97.0,<0.98`, `mcp>=1.27.0,<2`) supportent
    bien la stratégie retenue. Si A choisi → bump SDK
    Anthropic peut-être nécessaire.
