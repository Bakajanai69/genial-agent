## 📍 Contexte

Le **dogfooding S09.5** (golden pack G1-G5 joué en live le 2026-04-25,
cf. [`traces/S095_iterations.md`](../../traces/S095_iterations.md)) a
validé que l'offload générique du Payload Vault élimine la troncature
naïve (objectif principal de S09.5 : ✅). Mais il a aussi **mis en
lumière 3 axes de fragilité** qui dégradent l'expérience utilisateur,
sans pour autant remettre en cause l'architecture vault retenue :

1. **Robustesse de l'extraction sur schémas JSON inattendus** — le
   walker `payload_inspect` interprète mal certains paths (clés
   numériques traitées comme indices), et le skeleton ne donne pas
   assez de signal pour que l'agent choisisse le bon path du premier
   coup.
2. **Caps qui terminent brutalement la conversation** — quand un cap
   firefires (`cap_token_budget`, `cap_local_lookups_per_turn`), le
   tour s'arrête sans option utilisateur. La conversation devient un
   "dead end" alors que le contexte (notamment le vault) pourrait
   parfaitement être réutilisé sur un tour suivant.
3. **Coût tokens élevé sur conversations multi-rounds** — sans
   `prompt caching` activé, chaque round Claude re-tokenize l'intégralité
   du système + des tools + de l'historique cumulé. Cause directe du
   `cap_token_budget=80K` qui firefires souvent en fin de tour
   (déjà listé en next-step #1 du `README.md`).

Ces 3 axes se renforcent mutuellement : un cap qui firefires sur un
schéma incongru transforme une question résolvable en frustration
utilisateur. **L'objectif de S09.7 est de transformer ces frictions en
expérience fluide**, sans sacrifier la robustesse acquise par S09.5
ni introduire des sur-coûts non maîtrisés.

### Hors scope explicite (décision utilisateur 2026-04-25)

Cette story **n'aborde pas** les protections anti-abus (`MAX_$_PER_SESSION`,
rate-limit per-IP, idempotence cumulative, audit trail). À ce stade,
le projet privilégie la **qualité d'expérience utilisateur** sur les
mécanismes de protection commerciale (qui auront leur propre story
quand le déploiement passera de "démo évaluateur" à "produit"). La
phase 1 d'élicitation **ne doit pas** s'égarer sur ces sujets.

## 🎯 Scope

### Dans le scope

1. **Fix walker `_walk` de `payload_vault.py`** : le segment de path
   numérique pur (`"2023"`, `"775670417"`) doit pouvoir être interprété
   comme **clé string de dict** quand le nœud courant est un dict, pas
   forcément comme **index d'array**. La désambiguïsation est faite
   par le contexte (type de `cur`).
2. **Amélioration du skeleton et des hints** dans `build_index` :
   donner à l'agent assez de signal pour choisir le bon path du premier
   coup, sans hardcoder de logique métier (cf. contrainte S09.5
   "pas de hardcoding").
3. **Recalibrage des caps avec UX différenciée** :
   - Caps "compute pur" (lookups vault) : à relâcher.
   - Caps "argent" (Pappers credits, Anthropic tokens) : à conserver
     ou à bumper en concertation avec activation du prompt caching.
   - Caps qui firefires : transformer en **event UX continuable**
     plutôt que terminaison brutale.
4. **Activation Anthropic prompt caching** sur `system` + `tools`
   schema + messages N-1 (déjà listé en next-step #1 README, à
   intégrer dans cette story par cohérence : sans prompt caching, le
   relâchement du cap tokens deviendrait coûteux).
5. **Pack golden G1-G5 doit passer avec assertions resserrées** :
   - G2 : remonter la cible de 3 SIRENs vers 7-10 (story S09.5
     §"Métrique de succès objective" disait 10).
   - G4 : remonter l'assertion de "mention 'résultat net' + '2023'"
     vers "valeur exacte du résultat net 2023 citée".
6. **Pack adversarial S09 : 10/10 maintenu** (non-régression dure).
7. **Documentation** : update `traces/S095_iterations.md` (section
   "Après S09.7"), `README.md` (next-step #1 marqué livré),
   `docs/stories/README.md`.

  (cf. §"Hors scope explicite" du contexte). Story future quand le

## 📊 Observations factuelles — golden pack G2-G5 (live 2026-04-25)

Reproductible : `uv run python scripts/run_golden_S095.py`. Traces
JSONL complètes dans `traces/S095_*.jsonl`. Synthèse des 4 cas :

### G2 — *"Quels sont les mandats de Bernard Arnault ?"*

| Métrique | Observation |
|---|---|
| Routing | Haiku (par défaut, "mandats" pas dans `COMPLEX_PATTERNS`) |
| Pappers calls | 2 (`recherche-dirigeants` × 2 args différents) |
| Payloads offloadés | 2 (77K + 168K chars) |
| Local lookups | 4 (1 search regex + 3 inspects, dont 1 raté `[*]`) |
| Cap firefired | `cap_token_budget=80K` à mi-tour |
| SIRENs cités dans la réponse | **7** (cible story 10) |
| Marker "tronqué" | absent ✅ |

**Cause racine du gap 7 vs 10** : Pappers retourne 39 homonymes
"Bernard Arnault" → l'agent doit (a) disambiguer le "vrai" Arnault,
(b) extraire ses entreprises de `resultats[i].entreprises`, (c) lister
exhaustivement. Étapes (a) et (b) consomment ~80K tokens cumulés avant
que (c) ne soit complète.

**Tentative ratée notable** : `payload_inspect(json_path="$.resultats[*]")`
→ `_error: "key '*' missing at '$.resultats[*]'"`. Le walker ne
supporte pas le wildcard JSONPath. L'agent corrige seul mais consomme
1 lookup.

### G3 — *"Compare la santé financière de Carrefour vs Casino sur 3 ans"*

| Métrique | Observation |
|---|---|
| Routing | **Sonnet** (keyword "compare") |
| Pappers calls | 4 (2 sirenisateur + 2 comptes-entreprise avec `annee=2021,2022,2023`) |
| Payloads offloadés | 2 (240K + 161K chars) |
| Local lookups | 2 (searches multi-pattern très efficaces) |
| Cap firefired | `cap_token_budget=80K` en fin de stream (UX inchangée) |
| Réponse | Tableau 5 × 3 ans, **71 chiffres datés**, sourçage explicite |

**Verdict** : ✅ — le cas le plus complexe passe sans accroc, démonstration
de l'efficacité de `payload_search` regex multi-pattern sur les payloads
financiers. Note : 1 retry nécessaire au pytest (transient
`RateLimitError` Anthropic après ~10 min de tests cumulés).

### G4 — *"Quel est le résultat net de LVMH 2023 ?"*

| Métrique | Observation |
|---|---|
| Routing | Haiku |
| Pappers calls | 2 (sirenisateur + comptes-entreprise(annee=2023)) |
| Payloads offloadés | 1 (55K chars) |
| Local lookups | **5/5 (cap atteint)** sans extraction de la valeur |
| Tentatives ratées | `$.2023[0]` → `_error: "not a list at '2023'"` ; `$.2023` idem ; 2 searches regex `resultat.*net` → 0 matches |
| Inspect partiel | `$.comptes[0]` → 598 chars (compte 2024) |
| Réponse finale | 433 chars, **pas de valeur chiffrée**, mention "résultat net" + "2023" présente ✅ (assertion lâche) |

**Cause racine** : le payload Pappers a deux clés top-level `"2023"`
(string-key dict) et `"comptes"` (array). Le `_skeleton` rend
`"2023": ["<dict>[2 items]"]` qui ressemble à une liste, et le walker
traite tout segment numérique pur comme un index d'array — donc
`$.2023[0]` est interprété comme `node[2023][0]` au lieu de
`node["2023"][0]`. Bug réel du module S09.5 identifié post-merge.

### G5 — *"Liste les filiales de LVMH"*

| Métrique | Observation |
|---|---|
| Routing | Haiku |
| Pappers calls | 2 (sirenisateur + cartographie-entreprise) |
| Payloads offloadés | 1 (26K chars) |
| Local lookups | **1** inspect bien ciblé (`$.entreprises`) → 12K chars retournés |
| Cap firefired | `cap_token_budget=80K` en fin de stream (UX inchangée) |
| Réponse | **22 SIRENs distincts** structurés en 5 catégories |

**Verdict** : ✅ — cas idéal montrant qu'1 lookup suffit pour
extraire 100+ entités d'un payload de 26K chars. Pattern à généraliser.

## 🧭 Pistes d'amélioration — sans biais (la phase 1 arbitre)

> **Important pour l'agent d'élicitation** : ces pistes sont issues de
> l'analyse du dev S09.5 et du dialogue utilisateur post-livraison.
> Elles ne sont **pas** un cahier des charges figé. La phase 1 doit
> les évaluer, en proposer d'autres si pertinent (recherche web 2026,
> patterns Anthropic récents, blogposts MCP), et arbitrer sur quelles
> retenir avec leurs trade-offs explicités. Le dev agent n'implémente
> qu'après cet arbitrage.

### Axe 1 — Robustesse du walker JSON (`_walk` de `payload_vault.py`)

**Symptôme** : G4 — `$.2023[0]` rejeté parce que `"2023"` est traité
comme index alors que c'est une clé string. Aussi : `$.resultats[*]`
non supporté en G2.

**Pistes brutes (à arbitrer)** :

- **A1 — ✅ LIVRÉ EN S09.5 POST-REVIEW (2026-04-25)** Désambiguïsation
  par contexte : si `cur` est un dict → segment toujours interprété
  comme clé string ; si `cur` est une list → segment digit interprété
  comme index. Effort réel : ~5 lignes de code + 6 tests unit. Cf.
  [`traces/S095_iterations.md`](../../traces/S095_iterations.md)
  §"Step 4". **Reste à faire** : valider en live G4 dès retour des
  crédits Pappers et resserrer l'assertion `_has_resultat_net_2023`
  vers la valeur exacte du résultat net.
- **A2** Support du wildcard `[*]` (extraction de toutes les valeurs
  d'un array en une opération). Permet à l'agent de récupérer en 1
  call ce qui en demanderait N aujourd'hui (ex : tous les
  `resultats[i].entreprises` en G2). Trade-off : taille de retour
  potentiellement énorme → cap `max_chars` doit gérer.
- **A3** Support des paths bracketés style `$["2023"][0]` pour forcer
  l'interprétation clé-string même sans contexte. **Devient moins
  prioritaire après A1 livré** (la désambiguïsation par contexte couvre
  le cas usuel sans nécessiter une syntaxe alternative).
- **A4** Acceptation tolérante : si A1 échoue (clé string introuvable
  dans dict), tenter A2 (wildcard) ou retourner suggestion `_error`
  avec liste des clés disponibles. Le fix A1 améliore déjà les
  messages d'erreur (taille de la list, type du nœud) — A4 pourrait
  encore enrichir avec la liste des clés disponibles.

### Axe 2 — Skeleton plus informatif (`build_index`)

**Symptôme** : G4 — l'agent ne peut pas distinguer dict-avec-clé-numérique
d'un array dans le skeleton. G2 — l'agent ne sait pas que `resultats[0]`
peut ne pas être le "bon" Bernard Arnault parmi les 39.

**Pistes brutes (à arbitrer)** :

- **B1** Annotation explicite des dicts à clés numériques :
  `"_skeleton": {"2023": "<dict_key:str>"}` ou wrapping
  `"(str_key)2023": ...`.
- **B2** Profondeur adaptative selon densité : si le nœud à profondeur
  3 est un dict simple (≤ 5 clés), descendre à profondeur 4 ; sinon
  rester à 3.
- **B3** Sample d'un élément type dans les arrays : au lieu de
  `[" <dict>[39 items]"]`, exposer `[{"siren": "<str:9>", "nom_entreprise":
  "<str:N>", ...}, "...37 more items"]` pour que l'agent connaisse les
  champs sans avoir à inspecter.
- **B4** Hint contextuel dans `_inspect_hint` : générer dynamiquement
  une suggestion de path en se basant sur le squelette ("Si tu cherches
  une valeur dans un array trié, essaie `$.<array>[-1]` pour le dernier
  élément").

### Axe 3 — Recalibrage des caps & UX de continuation

**Symptôme** : G2 et G4 — caps firefires brutalement, l'agent s'arrête
sans option claire pour l'utilisateur. G2 : `cap_token_budget`. G4 :
`cap_local_lookups_per_turn`.

**Pistes brutes (à arbitrer)** :

- **C1** Bump `MAX_LOCAL_LOOKUPS_PER_TURN = 5 → 10` ou plus. Compute
  pur, zéro coût €. Effort : 1 ligne + ajustement tests.
- **C2** Bump `MAX_TOKENS_PER_SESSION = 80K → 150K` (ou plus, vérifier
  contexte 200K Sonnet 4.6). À combiner avec C5 sinon coût explose.
- **C3** Caps adaptatifs selon complexité détectée (`pick_initial_tier`
  S04 déjà existant) : Sonnet → budgets supérieurs, Haiku → budgets
  serrés. Cohérent avec philosophie routing existante.
- **C4** Cap **soft** = event "budget_warning" à 80% du budget +
  event "continuation_proposed" quand cap atteint, au lieu de
  termination brutale. UI Chainlit affiche `[Continuer] [Synthèse]` ;
  user clique → next turn avec vault préservé. Préserve l'UX flow
  conversationnel.
- **C5** Activation Anthropic prompt caching (`cache_control` sur
  system + tools schema + messages N-1). Réduit input tokens facturés
  ÷ 10 sur rounds 2+, TTFT ÷ 5-10. **Déjà listé en next-step #1
  README**, à intégrer ici par cohérence (sinon C2 explose le coût).
  Effort estimé : ~1h.

### Axe 4 — Routing keywords pour requêtes énumératives

**Symptôme** : G2 — "mandats de X" routé Haiku, qui sature à 7 résultats.
Sonnet aurait probablement listé les 10+ attendus en moins de tokens
grâce à sa meilleure synthèse.

**Pistes brutes (à arbitrer)** :

- **D1** Ajouter `mandats|filiales|liste\s+les?|énumère|tous\s+les` à
  `COMPLEX_PATTERNS` du pré-routeur. Trade-off : peut sur-router et
  augmenter le coût Sonnet (vérifier impact sur U1 / pack adversarial).
- **D2** Heuristique "queries énumératives détectées par length du
  retour Pappers attendu" — si l'agent vient de recevoir un payload
  > 50K avec un array > 20 items, escalader auto vers Sonnet pour
  l'extraction. Plus subtil que D1 mais plus coûteux à coder.
- **D3** Garder Haiku par défaut + améliorer son system prompt avec
  un exemple concret d'extraction multi-entités via vault. Approche
  prompt-engineering pure.

### Axe 5 — Field naming variability (cf. G4)

**Symptôme** : G4 — `payload_search(pattern="resultat.*net")` → 0 matches
parce que Pappers utilise `benefice_net` ou `resultat_de_lexercice`
selon les champs. L'agent ne devine pas les noms exacts.

**Pistes brutes (à arbitrer)** :

- **E1** Suggérer dans `_inspect_hint` un sample de paths tirés du
  skeleton pour que l'agent voie les vrais noms de champs. Cf. piste B4.
- **E2** Tool local supplémentaire `payload_keys(payload_id, json_path)`
  qui retourne uniquement les clés à un nœud donné, pour aider l'agent
  à explorer rapidement. Trade-off : 1 tool de plus à documenter dans
  le system prompt.
- **E3** Améliorer le hint pour pousser l'agent à inspecter d'abord
  un sample (`$.comptes[0]`) avant de lancer une regex globale —
  pattern d'introspection itérative.

### Méta-axe — Autres optimisations possibles

ci-dessus si la recherche web 2026 ou l'inspection du code en révèle.
Examples non-exhaustifs :

- **Compression du contexte historique** via `clear_tool_uses_20250919`

- **Persistance vault cross-turn** explicitement documentée (le vault
