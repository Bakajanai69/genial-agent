## 📍 Contexte

Pendant la review S09.5 (2026-04-25), le dogfooding live a révélé une
**anomalie côté serveur MCP Pappers** sur la gestion des crédits :

- Le pack mensuel **abonnement** (500 jetons / 20 €/mois) se vide
  rapidement (consommé en 1-2 jours sur du dev intensif).
- Pendant la fenêtre où l'abonnement est à 0 et que les jetons
  **Pay-As-You-Go (PAYG)** sont disponibles (souscription parallèle,
  jetons sans expiration), **le tool `comptes-entreprise` refuse les
  appels** alors que la doc Pappers indique explicitement :
  > *« Pay as You Go credits can take over in case the subscription
  > credits are entirely consumed »*
- Probe live (cf.
  [`scripts/probe_payg_compatibility.py`](../../scripts/probe_payg_compatibility.py))
  sur les 7 tools retenus :

  | Tool | PAYG accepté ? | Notes |
  |---|---|---|
  | `sirenisateur` | ✅ | 1 crédit |
  | `recherche-entreprises` | ✅ | 1 crédit, peut retourner CA/résultat via `return_fields` |
  | `cartographie-entreprise` | ✅ | 3 crédits |
  | **`comptes-entreprise`** | ❌ **refus** | seul tool retenu cassé |
  | `recherche-dirigeants` | ✅ | 1-4 crédits selon `par_page` |
  | `conformite-personne-physique` | ✅ | 0 crédit (gratuit) |
  | `recherche-beneficiaires` | n/a | bloqué par habilitation séparée |

  + `informations-entreprise` (exclu de `RETAINED_TOOLS`) : refus PAYG
  identique à `comptes-entreprise`.

- Conséquences observées sur les golden prompts :
  - **G1, G2, G4, G5** : couverts via `recherche-entreprises` (qui
    retourne `chiffre_affaires`, `resultat`, `capital`, `effectif`,
    `annee_finances` quand on lui passe les `return_fields` adéquats).
    Validé live le 2026-04-25 sur LVMH/Carrefour Hyper/Casino.
  - **G3 / U3 (comparaison multi-années Carrefour vs Casino)** : ne
    peut pas être résolu sans `comptes-entreprise` (les jetons
    abonnement seuls couvrent ce tool). Donc démo cassée si
    abonnement vide.

Cette story doit livrer une **stratégie de robustesse** qui :

1. Couvre **~95 %** des questions Fabien sans dépendre de
   `comptes-entreprise` quand l'abonnement est saturé.
2. **Préserve les crédits** Pappers via un cache persistant qui survit
   aux redémarrages (Railway free tier ou supérieur).
3. Refuse **proprement** les ~5 % de cas non couverts (scénarios
   nécessitant comptes-entreprise multi-années), avec un message
   clair pour l'utilisateur.

Cette story est explicitement **distincte de S09.7** qui traite la
robustesse extraction JSON et l'UX des caps internes (walker, skeleton,
prompt caching). S09.6 porte sur la **frontière externe** Pappers
(crédits, fallback tools, persistance cache).

### Inputs utilisateur (à confirmer en phase 1)

L'utilisateur (2026-04-25) a explicité :

- *« Couvrir 95 % des cas avec les tools fonctionnels, refuser
  proprement les 5 % restants en disant qu'on ne peut pas répondre
  à cette demande à cause d'un problème côté MCP Pappers. »*
- *« Cache persistant pour préserver les crédits : chaque requête
  identique doit servir depuis le cache, pas du MCP. »*
- *« Ne pas biaiser l'agent d'élicitation : on expose le problème +
  les pistes envisagées, mais l'agent tranche après recherches. »*

## 🧭 Pistes d'amélioration — sans biais (la phase 1 arbitre)

> **Important pour l'agent d'élicitation** : ces pistes sont issues
> du dialogue utilisateur post-review S09.5 et de l'observation live
> du bug PAYG. Elles ne sont **pas** un cahier des charges figé. La
> phase 1 doit les évaluer, en proposer d'autres si pertinent
> (recherche web 2026, patterns Pappers/MCP, ticket support Pappers
> entre-temps), et arbitrer sur quelles retenir avec leurs trade-offs
> explicités. Le dev agent n'implémente qu'après cet arbitrage.

### Axe 1 — Matrice tools/retours documentée

**Symptôme** : l'agent ne sait pas a priori que `recherche-entreprises`
peut retourner du financier via `return_fields`. Il essaie
`comptes-entreprise` par défaut (description plus explicite sur le
sujet "comptes annuels"), tombe sur le refus PAYG, et bascule
mal/incomplètement.

**Pistes brutes** :

- **A1** Capturer un échantillon **réel** (1 appel par tool,
  ~6 crédits PAYG max au total) et figer dans
  [`docs/pappers-mcp.md`](../pappers-mcp.md) §"Matrice tools" :
  `nom du tool` × `champs typiques retournés` × `taille indicative` ×
  `cas d'usage couvert`. Permet à l'agent de choisir le bon tool
  même quand la description Pappers est ambiguë.
- **A2** Enrichir le system prompt avec un bloc "carte des données"
  inspiré de A1, sans hardcoder de logique métier (juste un guide).
- **A3** Variante plus invasive : générer un **second `_inspect_hint`
  contextuel** par tool dans `mcp_pappers.py` qui dit explicitement
  *« Si tu cherches CA + résultat actuel, utilise `recherche-entreprises`
  avec ces `return_fields`. Si tu veux 3 ans détaillés, utilise
  `comptes-entreprise` (peut nécessiter un cache). »*. Risque :
  alourdit le prompt et frôle le hardcoding.

### Axe 2 — Logique de fallback en cas de refus crédits

**Symptôme** : actuellement, quand `comptes-entreprise` lève
`CreditsExhausted`, l'agent reçoit un message d'erreur générique et
peine à rebondir vers un autre tool.

**Pistes brutes** :

- **B1** Fallback **explicite côté code** : intercepter
  `CreditsExhausted(tool_name="comptes-entreprise")` dans
  `mcp_pappers.call_tool` et retourner automatiquement le résultat
  d'un appel `recherche-entreprises` équivalent. Trade-off : couplage
  de logique métier dans le client MCP, viole partiellement
  l'agnosticisme.
- **B2** Fallback **explicite côté agent** : enrichir le system prompt
  avec une consigne *« si un tool retourne une erreur de crédits,
  essaie un tool alternatif documenté dans la matrice ; si aucun
  ne suffit, dis poliment que tu ne peux pas répondre à cette
  question particulière car elle requiert un accès Pappers étendu. »*
  Plus propre architecturalement, mais dépend de la métacognition
  LLM (Haiku peut louper).
- **B3** Hybride : déclarer le fallback côté code (B1) **uniquement**
  pour la paire `comptes-entreprise` → `recherche-entreprises`, et
  laisser le système prompt gérer les autres cas via B2.
- **B4** Refus poli sans fallback : pour les cas où aucune alternative
  n'existe (ex : multi-années détaillées), message utilisateur clair
  *« Je ne peux pas accéder aux bilans détaillés multi-années en ce
  moment, mais voici les chiffres pour l'année courante : … »*. À
  combiner avec A1/B2.

### Axe 3 — Cache MCP persistant en production

**Symptôme** : le `mcp_cache.py` actuel (TTL 7j, persistance optionnelle
disque via env var) survit en local mais le filesystem Railway est
éphémère par défaut. Au cold start, le cache redémarre vide.

**Pistes brutes** :

- **C1** **Volume persistant Railway** (plan payant, ~5 €/mois) :
  config 5 min, transparent, propre. Volume monté sur `/data/`,
  env var `MCP_CACHE_PERSIST_PATH=/data/mcp_cache.json`. Trade-off :
  coût récurrent.
- **C2** **Bake `data/mcp_cache.json` dans l'image Docker** : gratuit
  (free tier OK), ~10 lignes Dockerfile (`COPY data/ /app/data/`),
  cache rechargé à chaque déploiement. Trade-off : cache figé entre
  deux builds — il faut rebuild + redeploy pour rafraîchir. OK si
  on rebuild quotidien, moins OK si on rebuild une fois par semaine.
- **C3** **Stockage externe** (Postgres free tier, Cloudflare R2,
  Redis cloud) : multi-instance, gratuit jusqu'à un volume modeste,
  mais ~1-2 h dev pour adapter le cache. Pertinent si l'agent
  passe en plusieurs instances Railway derrière un load balancer.
- **C4** **In-memory + pre-warm au boot** (déjà partiellement
  livré via `prewarm_cache()` dans `mcp_pappers.py`) : pas de
  persistance disque, mais on consomme quelques crédits abo au
  cold start pour réinitialiser. Acceptable si abo dispo.
- **C5** Combiner C2 + C4 : bake un cache "minimal viable" dans
  l'image (entités golden) ET pre-warm au boot pour les payloads
  manquants. Filet de sécurité double.

### Axe 4 — TTL du cache

**Symptôme** : le TTL actuel a été bumpé 24h → 7j en review S09.5
pour absorber la fenêtre du bug PAYG. Mais 7j peut être trop long
(données Pappers obsolètes) ou trop court (si Pappers met >7j à fixer
le bug et qu'on rebuild dans 8j).

**Pistes brutes** :

- **D1** Garder 7j pour la démo et basculer 24h après (cf. demande
  utilisateur 2026-04-25 explicitement « 24h »).
- **D2** TTL différencié par tool : 24h pour `sirenisateur` (peu
  changeant mais cheap à refresher), 7j pour `comptes-entreprise`
  (lourd + bug Pappers + données annuelles donc TTL long pertinent).
- **D3** TTL fonction de la fraîcheur des données Pappers : 1h pour
  les tools "live" (recherche, identité), 30j pour les tools
  "snapshots annuels" (comptes, bilans). Plus subtil mais demande
  un mapping explicite par tool.

### Axe 5 — Pré-warm intelligent

**Symptôme** : le `prewarm_persistent_cache.py` actuel relit les
traces JSONL et re-exécute les appels PAYG-compatibles. Mais il ne
peut pas pré-warmer `comptes-entreprise` tant que l'abonnement est
saturé.

**Pistes brutes** :

- **E1** Script déclenché **à chaque refill abo** (le 30/04 puis
  mensuellement) qui pré-warme automatiquement les payloads
  `comptes-entreprise` sur les 4 entités golden (LVMH, BNP, Carrefour,
  Casino) sur 3 années (2022-2024). Coût : ~24 crédits abo/mois,
  négligeable sur le pack 500.
- **E2** Pre-warm "à la demande" : la première requête utilisateur
  qui tombe sur un cache miss déclenche un appel live + cache la
  réponse pour les suivantes. Comportement actuel par défaut, OK
  tant que l'abo est dispo.
- **E3** Pre-warm "exhaustif" : générer toutes les combinaisons
  (4 entités × 7 tools × variantes args) au refill mensuel. Coût
  élevé (~100-200 crédits) mais cache 100 % couvert. Excessif pour
  4 entités golden mais à considérer si la liste s'étend.

### Axe 6 — Stratégie de gestion du refus utilisateur

**Symptôme** : pour les ~5 % de cas non couverts par les workarounds
(typiquement comparaison multi-années), il faut un message agent
honnête, pas une hallucination ni un crash UI.

**Pistes brutes** :

- **F1** Message générique cadré : *« Je n'ai pas accès aux comptes
  multi-années détaillés en ce moment. Voici les données disponibles
  pour la dernière année close : … »*. Combiné à A2/B2.
- **F2** Bandeau UI Chainlit dédié *« Mode dégradé : certains tools
  Pappers temporairement indisponibles, les requêtes qui en
  dépendent seront couvertes par les workarounds documentés. »*
  Activable via env var `PAPPERS_DEGRADED_MODE=true`. Cohérent avec
  R16 du cahier (mode dégradé cache-only) déjà partiellement prévu.
- **F3** Liste explicite en `EVALUATION.md` des questions qui
  peuvent rater + comment réagir si Fabien tombe dessus.

### Axe 7 — Ticket support Pappers (orthogonal)

Pas une piste code. Mais à tracer :

- **G1** Ouvrir un ticket [email protected] avec le diagnostic

  Pappers est du ressort de leur infra.
- **G2** Suivre la réponse, et **retirer le workaround** dès que

### Méta-axe — Autres pistes possibles

L'agent d'élicitation est libre de proposer d'autres pistes si la
recherche web 2026 ou l'inspection du code en révèle. Exemples
non-exhaustifs :

- **Idempotence cross-session** sur la clé `(tool, args_hash)` —
  permet à plusieurs instances Railway de partager le cache via un
  store externe (lien avec C3).
- **Compression des payloads cachés** (gzip côté disque) si le
  cache disque dépasse plusieurs Mo.
- **Health endpoint enrichi** qui interroge `/suivi-jetons` Pappers
  et expose le breakdown abo/PAYG dans `/health` Railway — permet
  un monitoring externe (UptimeRobot) qui alerte si l'abo est < 50.

- Pack adversarial S09 : **10/10 maintenu** (non-régression dure).

  PAYG (cap mou comme S09.5).
- **Mode dégradé prouvé** : la démo doit tourner **sans aucun appel
  `comptes-entreprise` live** quand le cache est pré-warmé (preuve :
  abonnement à 0 + pas de PAYG consommé sur U3).
