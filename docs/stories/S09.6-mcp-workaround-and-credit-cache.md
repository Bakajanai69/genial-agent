## 📍 Contexte

Pendant la review S09.5 (2026-04-25), le dogfooding live a révélé une
**anomalie côté serveur MCP Pappers** sur la gestion des crédits :

- Le pack mensuel **abonnement** (500 jetons / 20 €/mois) se vide
  rapidement (consommé en 1-2 jours sur du dev intensif).
- Pendant la fenêtre où l'abonnement est à 0 et que les jetons
  **Pay-As-You-Go (PAYG)** sont disponibles (souscription parallèle,
  jetons sans expiration), **le tool `comptes-entreprise` refuse les
  appels** alors que la doc Pappers indique explicitement :
  > *« Pay as You Go credits can take over in case the subscription
  > credits are entirely consumed »*
- Probe live (cf.
  [`scripts/probe_payg_compatibility.py`](../../scripts/probe_payg_compatibility.py))
  sur les 7 tools retenus :

  | Tool | PAYG accepté ? | Notes |
  |---|---|---|
  | `sirenisateur` | ✅ | 1 crédit |
  | `recherche-entreprises` | ✅ | 1 crédit, peut retourner CA/résultat via `return_fields` |
  | `cartographie-entreprise` | ✅ | 3 crédits |
  | **`comptes-entreprise`** | ❌ **refus** | seul tool retenu cassé |
  | `recherche-dirigeants` | ✅ | 1-4 crédits selon `par_page` |
  | `conformite-personne-physique` | ✅ | 0 crédit (gratuit) |
  | `recherche-beneficiaires` | n/a | bloqué par habilitation séparée |

  + `informations-entreprise` (exclu de `RETAINED_TOOLS`) : refus PAYG
  identique à `comptes-entreprise`.

- Conséquences observées sur les golden prompts :
  - **G1, G2, G4, G5** : couverts via `recherche-entreprises` (qui
    retourne `chiffre_affaires`, `resultat`, `capital`, `effectif`,
    `annee_finances` quand on lui passe les `return_fields` adéquats).
    Validé live le 2026-04-25 sur LVMH/Carrefour Hyper/Casino.
  - **G3 / U3 (comparaison multi-années Carrefour vs Casino)** : ne
    peut pas être résolu sans `comptes-entreprise` (les jetons
    abonnement seuls couvrent ce tool). Donc démo cassée si
    abonnement vide.

Cette story doit livrer une **stratégie de robustesse** qui :

1. Couvre **~95 %** des questions Fabien sans dépendre de
   `comptes-entreprise` quand l'abonnement est saturé.
2. **Préserve les crédits** Pappers via un cache persistant qui survit
   aux redémarrages (Railway free tier ou supérieur).
3. Refuse **proprement** les ~5 % de cas non couverts (scénarios
   nécessitant comptes-entreprise multi-années), avec un message
   clair pour l'utilisateur.

Cette story est explicitement **distincte de S09.7** qui traite la
robustesse extraction JSON et l'UX des caps internes (walker, skeleton,
prompt caching). S09.6 porte sur la **frontière externe** Pappers
(crédits, fallback tools, persistance cache).

### Axe 1 — Matrice tools/retours documentée

**Symptôme** : l'agent ne sait pas a priori que `recherche-entreprises`
peut retourner du financier via `return_fields`. Il essaie
`comptes-entreprise` par défaut (description plus explicite sur le
sujet "comptes annuels"), tombe sur le refus PAYG, et bascule
mal/incomplètement.

**Pistes brutes** :

- ✅ **A1 retenu** Capturer un échantillon **réel** (1 appel par tool,
  ~6 crédits PAYG max au total) et figer dans
  [`docs/pappers-mcp.md`](../pappers-mcp.md) §"Matrice tools" :
  `nom du tool` × `champs typiques retournés` × `taille indicative` ×
  `cas d'usage couvert`. Permet à l'agent de choisir le bon tool
  même quand la description Pappers est ambiguë. **Réutilise le probe
  `probe_comptes_entreprise_alternatives.py` déjà livré.**
- ✅ **A2 retenu** Enrichir le system prompt avec un bloc "carte des
  données" inspiré de A1, sans hardcoder de logique métier (juste un
  guide). **Snippet figé §"Architecture phase 1 — Axe 1".**
- ❌ **A3 rejeté** Variante plus invasive (`_inspect_hint` contextuel
  par tool dans `mcp_pappers.py`) qui dit explicitement *« Si tu
  cherches CA actuel, utilise `recherche-entreprises` avec ces
  `return_fields` … »*. Rationale rejet : alourdit le prompt sur tous
  les tours, frôle le hardcoding métier (reproche S09.5), et A1+A2
  donne ~95 % du gain pour 30 % de l'effort.

### Axe 2 — Logique de fallback en cas de refus crédits

**Symptôme** : actuellement, quand `comptes-entreprise` lève
`CreditsExhausted`, l'agent reçoit un message d'erreur générique et
peine à rebondir vers un autre tool.

**Pistes brutes** :

- ❌ **B1 rejeté** Fallback **uniquement côté code** : trop fragile
  (couplage métier total dans `mcp_pappers.py`, perte de la
  transparence agent → l'agent croit qu'il a appelé `comptes-entreprise`
  alors que le code a substitué `recherche-entreprises`).
- ❌ **B2 rejeté seul** Fallback **uniquement côté agent** :
  trop dépendant de la métacognition Haiku (peut louper), pas de
  filet de sécurité.
- ✅ **B3 retenu** Hybride : **transformation enrichie côté code** —
  quand `comptes-entreprise` lève `CreditsExhausted`, `mcp_pappers.py`
  ne substitue PAS l'appel mais retourne un `tool_result` structuré
  qui dit explicitement à l'agent *« comptes-entreprise indisponible
  (crédits abo épuisés + bug PAYG Pappers) — workaround disponible :
  appelle `recherche-entreprises(siren=…, return_fields=[…])` pour
  les chiffres headline année courante, ou refuse poliment pour
  multi-années »*. L'agent **garde la décision** (transparence) mais
  reçoit l'info dont il a besoin pour rebondir. **Snippet §"Architecture
  phase 1 — Axe 2".**
- ✅ **B4 conservé en complément** : pour les cas multi-années non
  couverts par le workaround, le system prompt contient déjà la règle
  "jamais d'hallucination" — on l'étend avec un script de refus poli
  type *« Les comptes détaillés multi-années Pappers ne sont pas
  accessibles en ce moment ; voici les données disponibles pour la
  dernière année close : … »*. Snippet §"Architecture phase 1 —
  Axe 6".

### Axe 3 — Cache MCP persistant en production

**Symptôme** : le `mcp_cache.py` actuel (TTL 7j, persistance optionnelle
disque via env var) survit en local mais le filesystem Railway est
éphémère par défaut. Au cold start, le cache redémarre vide.

**Pistes brutes** :

- ✅ **C1 retenu en complément (décision Q1, 2026-04-26)** **Volume
  persistant Railway trial** (0,5 GB inclus pendant les 30 j de trial,
  déduit des $5 crédits — coût négligeable pour ~500 KB de données).
  Volume monté sur `/data`, env var
  `MCP_CACHE_PERSIST_PATH=/data/mcp_cache.json`. Trade-off : volume
  supprimé 30 j après expiration trial — OK pour démo 1-2 semaines.
- ❌ **C2 (seul) rejeté** Bake `data/mcp_cache.json` dans l'image
  Docker isolé : sans pre-warm boot, refresh trop figé.
- ❌ **C3 rejeté** Stockage externe (Postgres free tier, Cloudflare
  R2, Redis cloud) : multi-instance, mais ~1-2 h dev pour adapter le
  cache, et on n'a qu'**une seule instance Railway** (pas de LB) →
  over-engineering pour démo.
- ❌ **C4 (seul) rejeté** In-memory + pre-warm au boot uniquement :
  consomme des crédits **à chaque cold start** sur free tier (un sleep
  toutes les ~10 min = ~6 cold starts/heure si trafic).
- ✅ **C5 + C1 retenu (hybride, décision Q1)** : combiner **bake
  Docker + volume Railway trial** :
  - **Bootstrap** : `data/mcp_cache.json` (390 KB) et
    `data/cl_threads.db` (snapshot session démo) **versionnés** dans
    le repo (gitignore retiré — données Pappers publiques, pas de
    PII). Bake via `COPY data /app/data` dans `Dockerfile`.
  - **Runtime** : volume Railway monté sur `/data` (config dashboard
    1 fois). Au boot, si `/data/mcp_cache.json` n'existe pas, on
    copie depuis `/app/data/mcp_cache.json` (bootstrap auto).
    Idem `cl_threads.db`. Ensuite, le code lit/écrit toujours sur
    `/data/...`, donc le volume accumule les nouveautés runtime.
  - **Pre-warm boot** : `prewarm_cache()` enrichit best-effort,
    n'échoue pas si crédits épuisés.
  - **Refresh manuel** : `make prewarm-comptes` (consomme crédits
    abo) écrit dans `data/mcp_cache.json` local → commit → push →
    nouveau build. Au boot, le bake est plus récent que le volume
    si l'image embarque `data/mcp_cache.json` fraîchement
    pre-warmé : on garde le fichier le plus volumineux/récent
    (logique de fusion documentée snippet ci-dessous).
  - **Filet de sécurité triple** : bake (garantie minimum viable
    sur 4 entités golden) + volume (continuité runtime entre
    rebuilds) + pre-warm boot (auto-réparation si cache miss).
  - Snippet Dockerfile + boot script §"Architecture phase 1 —
    Axe 3 (révisé)".

### Axe 4 — TTL du cache

**Symptôme** : le TTL actuel a été bumpé 24h → 7j en review S09.5
pour absorber la fenêtre du bug PAYG. Mais 7j peut être trop long
(données Pappers obsolètes) ou trop court (si Pappers met >7j à fixer
le bug et qu'on rebuild dans 8j).

**Pistes brutes** :

- ❌ **D1 rejeté** TTL uniforme : la donnée annuelle (`comptes-entreprise`)
  ne change pas pendant 365 j, alors que `sirenisateur` peut bouger
  (changement de raison sociale, fusion). Mauvaise calibration.
- ✅ **D2 retenu** TTL différencié par tool, mappé en code :
  - **24 h** : `sirenisateur`, `recherche-entreprises`,
    `recherche-dirigeants`, `conformite-personne-physique` (tools
    "live").
  - **7 j** : `comptes-entreprise`, `cartographie-entreprise` (tools
    "snapshots" annuels — peu volatils + lourds en crédits).
  - Implémentation : ajouter `TOOL_TTL_OVERRIDES: dict[str, int]` dans
    `mcp_cache.py`, lecture dans `set()`. **Snippet §"Architecture
    phase 1 — Axe 4".**
- ❌ **D3 rejeté** Mapping plus fin (1 h / 30 j) : sur-optimisation.
  D2 capture 95 % du gain.

### Axe 5 — Pré-warm intelligent

## 🧠 Logique de cache MCP — lecture rapide (phase 1)

> Bloc à lire avant phase 2 — clarifie ce qui consomme un crédit
> Pappers et ce qui n'en consomme pas. Référence pour comprendre les
> métriques de succès §"Métrique de succès objective".

**Clé de cache** : `(tool_name, sha256(args_canonical))` — cf.
[`mcp_cache.py:166-176`](../../src/genial_agent/mcp_cache.py).
**Deux appels avec le même tool ET les mêmes arguments partagent la
même clé**, donc une seule charge réseau.

**Workflow `call_tool`** ([`mcp_pappers.py:405-475`](../../src/genial_agent/mcp_pappers.py)) :

1. `cache.get(tool, args)` → si **hit** → return immédiat, **0 crédit
   consommé** (le compteur `pappers_calls_today` n'est pas incrémenté
   non plus).
2. Si **miss** → `cache.single_flight(...)` coalesce les appels
   concurrents sur la même clé (3 onglets simultanés sur la même
   question = 1 seul crédit).
3. Si la réponse arrive sans erreur métier → `cache.set(tool, args,
   payload)` + `_stats_incr(pappers_calls_today=1)`.
4. **Erreurs métier non cachées** : `CreditsExhausted`,
   `PappersToolError` ne sont pas mis en cache (sinon on
   "empoisonnerait" le cache avec une erreur transitoire).

**Conséquences pour les golden G1-G5** :

| Tour | Détail | Crédits live (1ʳᵉ exécution) | Crédits live (2ᵉ exécution) |
|---|---|---:|---:|
| G1 *"CA Carrefour"* | `sirenisateur(Carrefour)` + `recherche-entreprises(siren=…, return_fields=[CA, …])` | 2 | 0 (cache hit) |
| G2 *"Mandats Bernard Arnault"* | `recherche-dirigeants(q="Bernard Arnault")` | 1-4 | 0 (cache hit) |
| G3 *"Compare Carrefour vs Casino 3 ans"* | `sirenisateur(Carrefour)` 🟢 + `sirenisateur(Casino)` + 6× `comptes-entreprise(siren, annee)` | ~7 (sans pre-warm) ou **0** (avec pre-warm) | 0 |
| G4 *"Résultat net LVMH 2023"* | `sirenisateur(LVMH)` + `comptes-entreprise(LVMH, 2023)` | 2 (sans pre-warm) ou **0** (avec pre-warm) | 0 |
| G5 *"Filiales LVMH"* | `cartographie-entreprise(siren=…)` | 3 | 0 (cache hit) |

**Pré-warm (Axe 5)** : on pré-charge à l'avance les ~15 combinaisons
attendues sur les 4 entités golden (LVMH, BNP, Carrefour, Casino) ×
3 années (2022-2024) pour `comptes-entreprise`, + sirenisateurs et
return_fields headline. **Une fois le bake committé, les golden G1-G5
doivent passer en 0 crédit live** (modulo `recherche-dirigeants(q="Bernard
Arnault")` qui n'est pas pré-warmable car args texte libre — 1ʳᵉ
exécution = 1 crédit, ensuite cache hit).

**Ce qui CASSE le cache** (cas où l'agent re-consomme un crédit pour
une question voisine) :

- L'agent appelle `recherche-entreprises(siren=X, return_fields=[CA])`
  puis `recherche-entreprises(siren=X, return_fields=[CA, resultat])`
  → deux clés distinctes (args différents).
- L'agent demande `comptes-entreprise(siren=X, annee=2025)` (année
  pas dans le pre-warm) → cache miss, appel live.
- L'agent appelle `recherche-dirigeants(q="B. Arnault")` puis
  `recherche-dirigeants(q="Bernard Arnault")` → deux clés distinctes
  (le hash dépend de la chaîne exacte).

**Garantie pour la démo Fabien** : tant que Fabien clique sur les
4 starters (qui sont fixes) → 0 crédit live, latence purement
Anthropic. S'il tape une question libre sur une nouvelle entité (e.g.
"Total"), le sirenisateur tape live (1 crédit), puis tout le reste
de la conversation sur Total est cachée.

→ **Cohérence avec Q2** : les assertions resserrées G2 ≥ 5 / G4
chiffré sont robustes parce qu'elles s'appuient sur le cache pré-warmé
**sans dépendre** de l'état des crédits abo Pappers au moment de la démo.

```python
# Nouveau module : src/genial_agent/data_bootstrap.py (~30 lignes).
# Appelé une seule fois au démarrage app, AVANT que le ToolCache et
# le ChainlitDataLayer ne lisent leurs fichiers.

from pathlib import Path
import shutil
import structlog

logger = structlog.get_logger(__name__)

VOLUME_DIR = Path("/data")
BAKE_DIR = Path("/app/data")
BOOTSTRAP_FILES = ("mcp_cache.json", "cl_threads.db")


def bootstrap_volume_from_bake() -> None:
    """Copie les fichiers bake vers le volume Railway si absents.

    No-op en local (le volume /data n'existe pas, on tombe dans le
    except). No-op si le volume contient déjà les fichiers (cas
    standard runtime, on préserve l'état accumulé).
    """
    if not VOLUME_DIR.exists():
        logger.info("bootstrap_skip", reason="volume_dir_absent")
        return
    for fname in BOOTSTRAP_FILES:
        target = VOLUME_DIR / fname
        source = BAKE_DIR / fname
        if target.exists():
            logger.info("bootstrap_skip", file=fname, reason="volume_has_file")
            continue
        if not source.exists():
            logger.warning("bootstrap_skip", file=fname, reason="bake_absent")
            continue
        shutil.copy2(source, target)
        logger.info("bootstrap_copy", file=fname, size=target.stat().st_size)
```

```python

# Module-level : exécuté une seule fois au démarrage process Chainlit.
bootstrap_volume_from_bake()
```
